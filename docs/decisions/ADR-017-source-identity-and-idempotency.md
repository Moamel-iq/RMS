# ADR-017 — Source identity and idempotency

- **Status:** Accepted. **Implemented by Task 0.7.**
- **Date:** 2026-08-09
- **Related:** ADR-013 (periods), ADR-014 (chart of accounts), ADR-016 (scope)

## Decision

Every journal generated by an upstream module carries a **source identity**:

```
organization + source_document_type + source_document_id + source_event
```

for example `KM / PURCHASE_INVOICE / 145 / POSTED`. At most one journal in an
organization may hold a given identity, enforced by a partial unique index.

Purchases, Inventory, Sales, and Payroll will retry — a timeout, a duplicated
message, a second click. The same economic event must not become two journals,
and the guarantee has to hold when nothing is checking it in Python, because
two concurrent workers can both pass a `SELECT` before either has inserted.

### `source_event` is a closed enum

`POSTED` and `REVERSED`, as `TextChoices` **and** a database `CheckConstraint`.

A free string would let one typo defeat the guarantee whose entire job is to
catch a retry. `POSTEED` would sit outside the unique index while looking, to
a reader, exactly like an entry inside it — the worst kind of failure, because
it presents as correct.

Extended intentionally, with code and tests, when a module genuinely needs
another distinct accounting event for the same source object. `VOIDED`,
`ADJUSTED`, `PAID`, and `SETTLED` are deliberately absent until something
actually requires them.

### `source_event` is not `status`

| | Describes | Changes |
|---|---|---|
| `JournalEntry.status` | the lifecycle of the journal | DRAFT → POSTED → REVERSED |
| `source_event` | the upstream economic event that caused it | never |

`PURCHASE_INVOICE / 145 / POSTED` names the original posting for invoice 145
forever, whatever later happens to the journal carrying it. When that journal
is reversed, its `status` becomes `REVERSED` and its `source_event` stays
`POSTED`; the *reversal* is a second journal holding
`PURCHASE_INVOICE / 145 / REVERSED`.

### All three fields or none

A manual journal has no upstream document and correctly carries none of them.
A half-populated identity is refused by a check constraint and by the service.

This is not tidiness. The unique index is **partial on `source_event`**, so an
entry carrying a type and an id but no event would fall *outside* the
guarantee — indistinguishable, on screen, from one inside it. The index is
partial so that manual journals do not all collide with each other on three
empty strings.

### Retry versus conflict

Two keys answer two questions, and the service combines them into one rule:

| Presented | Meaning | Result |
|---|---|---|
| Same `idempotency_key` | the same *command* again | the existing entry is returned |
| Same source identity, different key | a new command for an event already recorded | `source_event_already_posted` |

Neither path can create a second journal, and neither surfaces a raw
`IntegrityError`. The conflict is a domain error naming the entry that already
holds the event, so an operator can go and look at it.

### Immutable once posted

`organization`, `source_document_type`, `source_document_id`, and
`source_event` cannot be changed on a posted entry. A guarantee that can be
edited afterwards is not a guarantee: repointing an entry would free its
identity to be claimed a second time, and the unique index would raise no
objection because nothing would be duplicated at that instant.

Enforced by the `accounting_posted_entry_is_immutable` trigger, with its own
error message — "you moved the source identity" and "you edited a posted
entry" send a developer to two different places.

### A reversal cannot itself be reversed

It would need to claim `.../ REVERSED` a second time. Reported as
`cannot_reverse_a_reversal` rather than left to collide on the index, and the
accounting answer was never a third mirror: post a replacement entry.

## Alternatives considered

- **`idempotency_key` alone**, as Task 0.6 left it. Unique, and it depends on
  every caller composing the key identically forever. Two modules with two
  conventions produce two journals for one invoice and neither is wrong on its
  own terms.
- **A free-text `source_event`.** Flexible, and one typo silently defeats the
  uniqueness guarantee.
- **Reusing `status` as the source event.** They look similar until the first
  reversal, at which point the original's identity would change from `POSTED`
  to `REVERSED` and collide with the reversal's.
- **Catching `IntegrityError` and returning the existing row.** Makes a retry
  work and hides a genuine conflict — a caller sending a different command for
  the same event would silently receive a journal they never asked for.
- **A global unique index, not per organization.** Two organizations each
  number their purchase invoices from 1, so the second organization's invoice
  145 would be unpostable.

## Consequences

- Upstream modules must supply all three fields or none. Phase 1 onward.
- The names are `source_document_type` and `source_document_id`, not
  `source_type`/`source_id`: `AuditEvent` already uses them, and one
  vocabulary across the two is worth more than a shorter one here. They mean
  exactly source type and source id.
- The index is partial, so manual journals are unconstrained by it and remain
  protected by `idempotency_key` alone.
- Reversing a reversal is refused. Replacement is the documented correction.
