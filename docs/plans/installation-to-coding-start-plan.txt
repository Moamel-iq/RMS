KHAN MANDI RESTAURANT MANAGEMENT SYSTEM
WINDOWS INSTALLATION AND CODING START PLAN
Prepared: 7 August 2026

======================================================================
1. PURPOSE
======================================================================

This plan takes the project from a clean Windows computer to the first
safe coding milestone for the Khan Mandi Restaurant Management System.

The recommended development path is:

- Windows 11, native development.
- PyCharm as the IDE.
- Git and a private GitHub repository.
- Python 3.14, latest patch release.
- Django 5.2 LTS, latest security patch in the 5.2 series.
- PostgreSQL 18, latest supported minor release.
- Django Ninja for the API.
- Standard Python virtual environment plus pip-tools.
- pytest, factory_boy, Hypothesis, Ruff, mypy, and pre-commit.
- Claude Code connected to PyCharm through the official JetBrains
  integration.
- Local PostgreSQL first. Docker, Redis, Celery, and PDF tooling are
  added only when the project reaches the feature that needs them.

The goal is not merely to make Django display its welcome page. The goal
is to create a reproducible, tested, secure foundation that can support
inventory, purchases, recipes, sales, accounting, HR, and reports
without needing a restart later.

======================================================================
2. FIXED TECHNICAL DECISIONS
======================================================================

Use these decisions unless a written Architecture Decision Record changes
one of them:

1. Python:
   Python 3.14, latest 3.14.x patch.
   Python 3.14.7 was current when this plan was prepared.

2. Django:
   Django 5.2 LTS, always upgraded to the latest 5.2.x security release.
   Use a compatible version constraint such as Django~=5.2.0 in the
   direct dependency file, then lock the exact installed version.

3. Database:
   PostgreSQL 18, latest 18.x minor release.
   PostgreSQL 18.4 was current when this plan was prepared.
   Do not use PostgreSQL 19 beta for this project.

4. API:
   Django Ninja with typed request and response schemas.

5. Package management:
   Python venv + pip-tools.
   Direct dependencies live in requirements.in and requirements-dev.in.
   Exact dependency versions are generated into requirements.txt and
   requirements-dev.txt.

6. Project architecture:
   - Thin API/view layer.
   - Service layer for commands and business transactions.
   - Selector/query layer for complex reads.
   - Database constraints for invariants that the database can enforce.
   - transaction.atomic() around each complete posting operation.
   - No financial or stock business logic hidden in serializers, views,
     admin actions, signals, or model save() methods.
   - Signals are not used for essential financial posting.

7. Financial rules:
   - Decimal for money, quantities, rates, percentages, unit costs, and
     conversion factors.
   - Never use float for financial or stock calculations.
   - Posted stock and accounting ledger effects are append-only.
   - Corrections use reversal and replacement transactions.
   - Moving weighted-average inventory costing.
   - Negative stock is rejected during normal posting.
   - Every money- or stock-touching service must have tests.

8. Branch design:
   - Organization is the top business boundary.
   - Branch is a child of Organization.
   - Not every table receives a Branch foreign key automatically.
   - Global/master records and branch-owned transaction records are
     modeled deliberately.
   - Branch-local business date is separate from timestamp and supports
     operations after midnight.

9. Language and time:
   - UTF-8 everywhere.
   - English and Arabic are supported.
   - System timezone: Asia/Baghdad.
   - USE_TZ remains enabled.
   - Store timestamps in timezone-aware form.
   - Arabic/RTL support is included from the foundation, not postponed
     until reports.

10. AI usage:
    - Claude works one small task at a time.
    - Claude first plans and writes or updates tests.
    - You review every diff involving stock, money, commissions, payroll,
      unit conversions, dates, and permissions.
    - Claude may never reset a database, delete migrations, reveal
      secrets, or bypass safety permissions without explicit approval.

7. STAGE 3 — INSTALL POSTGRESQL
======================================================================

Install PostgreSQL 18 using the supported Windows installer.

Select:

- PostgreSQL Server.
- Command Line Tools.
- pgAdmin.
- Stack Builder is optional and is not required for the first milestone.

Recommended local settings:

- Port: 5432, unless another PostgreSQL instance already uses it.
- Locale: keep a modern UTF-8-compatible default.
- Superuser: postgres.
- Password: create a strong password and store it in a password manager.

Never use the postgres superuser as the Django application user.

After installation:

1. Confirm the PostgreSQL Windows service is running.

2. Verify from SQL Shell or by using the full path:

    "C:\Program Files\PostgreSQL\18\bin\psql.exe" --version

3. Open SQL Shell as the postgres administrator and create a local
   development role and database:

    CREATE ROLE khan_mandi_dev
        WITH LOGIN
        CREATEDB
        NOSUPERUSER
        NOCREATEROLE;

    \password khan_mandi_dev

    CREATE DATABASE khan_mandi_dev
        WITH OWNER = khan_mandi_dev
        ENCODING = 'UTF8';

    \q

Why CREATEDB is allowed here:
Django's automated tests may create a temporary test database. This is
acceptable for the local development role. A production application role
must not receive CREATEDB, CREATEROLE, or SUPERUSER privileges.

Use a unique strong password. Do not copy a sample password from a plan,
prompt, README, or chat.

Optional connection verification:

    "C:\Program Files\PostgreSQL\18\bin\psql.exe" ^
        -h 127.0.0.1 -p 5432 -U khan_mandi_dev -d khan_mandi_dev

Inside psql:

    SELECT current_database(), current_user, version();
    \q

14. STAGE 10 — CREATE FOUNDATION APPS IN THE CORRECT ORDER
======================================================================

Create and implement these apps one task at a time.

A. apps.core

Purpose:

- Common abstract timestamp model.
- Safe shared utilities.
- Correlation/request ID support later.
- No generic "everything" model dumping ground.
- No business-specific logic.

B. apps.users

Create the custom User model before the first migration.

Recommended starting point:

- Extend Django AbstractUser.
- Keep authentication simple initially.
- Add only fields required by the SRS.
- Do not make branch ownership a single field directly on User.
- Model organization/branch membership separately.

Immediately set:

    AUTH_USER_MODEL = "users.User"

Do this before running migrate.

C. apps.organizations

Initial concepts:

- Organization.
- Branch.
- Organization membership.
- Branch membership or branch access assignment.
- Role/permission mapping.
- Branch timezone.
- Branch business-day cutoff time.
- Bilingual names where required.
- Active/inactive status.
- Uniqueness constrained within the correct organization.

Do not implement every operational location here. Warehouse, kitchen
location, and cash point can be introduced by their owning modules unless
the SRS requires a shared location abstraction.

D. apps.units

Initial concepts:

- Unit dimension, such as MASS, VOLUME, COUNT, LENGTH.
- Unit of measure.
- Base conversion within a dimension.
- Decimal conversion factors.
- Validation that incompatible dimensions cannot convert.
- Item-specific package conversions are added with the Item model in
  Inventory.
- Production yield is not a unit conversion.

Examples:

- kg to g is a unit conversion.
- one rice sack to 30 kg is item/package-specific.
- 10 kg raw meat to 8.7 kg cooked output is production yield.

E. apps.accounting

At this stage, create only the thin accounting kernel and invariants,
not the complete chart of accounts.

The first kernel must support or define:

- Journal entry header.
- Journal lines.
- Debit and credit decimal amounts.
- Source document type and ID.
- Organization and branch context where applicable.
- Accounting date and document date.
- Idempotency key.
- Draft and posted state.
- Balanced-entry validation.
- Atomic posting.
- Reversal reference.
- No edit/delete of posted lines.

Do not let Inventory, Purchasing, HR, or Sales construct arbitrary
accounting logic in their views. Accounting posting policies will map
domain events to journal lines.

17. STAGE 13 — CONFIGURE TESTING AND CODE QUALITY
======================================================================

Place configuration in pyproject.toml where supported.

Configure pytest-django:

- DJANGO_SETTINGS_MODULE = config.settings.test
- Clear test file naming.
- Coverage for apps and important config code.
- Warnings visible rather than silently ignored.

Minimum test categories for Phase 0:

1. User model:
   - User creation.
   - Superuser creation.
   - Authentication behavior.
   - No accidental dependency on the default auth.User model.

2. Organization and Branch:
   - Branch belongs to one organization.
   - Required uniqueness rules.
   - Inactive branch behavior.
   - User cannot access an unassigned branch.
   - Cross-organization access is rejected.

3. Units:
   - Positive Decimal conversion factor.
   - Same-dimension conversion works.
   - Cross-dimension conversion fails.
   - Float input is rejected or normalized according to the written
     policy.
   - Precision and rounding policy is tested.

4. Accounting kernel:
   - Balanced entry posts.
   - Unbalanced entry is rejected.
   - A duplicate idempotency key does not double-post.
   - A failure rolls back the entire transaction.
   - Posted lines cannot be edited or deleted through normal services.
   - Reversal references the original entry.

5. API:
   - Health endpoint schema and status.
   - Authentication/authorization foundations where applicable.

6. Settings:
   - Test uses PostgreSQL configuration.
   - Production settings reject missing secrets.
   - Timezone is Asia/Baghdad.

Configure Ruff for:

- Linting.
- Import order.
- Formatting.
- Reasonable Django exclusions.
- Migrations excluded from inappropriate formatting rewrites.

Configure mypy with django-stubs.

Configure pre-commit to run at least:

- Trailing whitespace checks.
- End-of-file checks.
- YAML/TOML validation.
- Ruff lint.
- Ruff format check.
- Secret detection or an approved equivalent.
- Optional mypy on the appropriate scope.

    & .\.venv\Scripts\pre-commit.exe install

## Architecture rules

- Thin API/views.
- Commands and state changes live in explicit service functions.
- Complex reads live in selectors/query services.
- Posted inventory and accounting effects are append-only.
- Corrections use reversal and replacement.
- Use Decimal, never float, for money, quantities, rates, unit costs,

- Use moving weighted-average inventory costing.
- Reject negative stock during normal posting.
- Use transaction.atomic() for complete posting operations.
- Use idempotency for operations that may be retried.
- Never hide essential posting logic in signals or model save().
- Do not add Branch FK to every model automatically.
- Enforce organization/branch access in services and queries.
- Use Asia/Baghdad and a separate branch business date.
- Preserve Arabic text and RTL requirements.
- Every money- or stock-touching function requires tests.
- Prefer database constraints for enforceable invariants.
- Use reversal, never deletion, for posted financial records.

## Safety rules

- Delete migration files.
- Reset, flush, or drop a database.
- Run destructive SQL.
- Read, print, copy, or commit .env secrets.
- Commit personal employee, payroll, supplier, or investor data.
- Install a new dependency.
- Modify multiple modules in one task.
- Use --dangerously-skip-permissions.
- Change an accepted accounting, costing, or rounding policy.
- Mark tests as skipped merely to make the suite pass.

27. COMMON WINDOWS PROBLEMS
======================================================================

PROBLEM:
django-admin is not recognized.

SOLUTION:
Use the project interpreter directly:

    & .\.venv\Scripts\python.exe -m django startproject config .

PROBLEM:
Activate.ps1 cannot be loaded because running scripts is disabled.

SOLUTION:
Do not activate. Configure PyCharm to use:

    .venv\Scripts\python.exe

Run commands with the explicit executable path.

PROBLEM:
No module named django.

SOLUTION:
PyCharm or the terminal is using the wrong interpreter. Verify:

    & .\.venv\Scripts\python.exe -m django --version

PROBLEM:
psql is not recognized.

SOLUTION:
Use the full executable path:

    "C:\Program Files\PostgreSQL\18\bin\psql.exe"

Or add PostgreSQL's bin directory to PATH, then restart terminals.

PROBLEM:
Password authentication failed for user khan_mandi_dev.

SOLUTION:
Check:

- DB_USER in .env.
- DB_PASSWORD in .env.
- Correct port.
- Correct database name.
- PostgreSQL service status.
- The role password through \password.
- No hidden whitespace copied into .env.

Do not solve this by using the postgres superuser in Django.

PROBLEM:
PyCharm shows unresolved Django imports.

SOLUTION:
Select:

    <project>\.venv\Scripts\python.exe

Then refresh/synchronize the interpreter packages.

PROBLEM:
Claude command is not found inside PyCharm.

SOLUTION:

- Restart PyCharm completely.
- Run where.exe claude in a normal PowerShell window.
- Check the Claude Code plugin setting for the command path.
- Use the full path if necessary.
- Reopen the project terminal.

PROBLEM:
Claude Code cannot detect PyCharm.

SOLUTION:

- Install/restart the official JetBrains plugin.
- Start Claude from PyCharm's integrated terminal, or use /ide from an
  external Claude session.
- Ensure Claude and PyCharm point to the same project folder.

PROBLEM:
Django created db.sqlite3.

SOLUTION:
Stop. Verify the local settings module and PostgreSQL environment values.
Remove an unused local SQLite file only after confirming that it contains
no needed data. Never continue business development with an accidental
SQLite configuration.

PROBLEM:
Migrations were applied before AUTH_USER_MODEL was configured.

SOLUTION:
For an empty local development database only, recreate the database and
apply migrations after the custom User model is configured. For any
database containing valuable data, create a reviewed migration plan;
never delete migrations or drop data casually.
